# 区域草稿与权威查询预览（Zone Answer Studio）

一个**本机运行、带真实服务端状态**的内部 DNS 区域编辑与权威查询预览工具。
你在草稿里改记录、发查询，服务端按区域（zone）的权威语义计算应答；确认无误后再把草稿
发布成不可变版本。它**不访问公共 DNS、不注册域名、不管理云账号**——只回答“这个工具自己
保存的区域，在给定查询下会给出什么权威结果”。

## 解决的核心痛点

- **改一行不是一行的事**：把应用域名改成 CNAME，同名的其它记录可能与之冲突；这些冲突在
  “校验”里按阻塞错误列出，并**归因到具体的草稿改动编号**。
- **委派之后父区不该继续作答**：子域一旦有 NS，其下名字只返回父区的**转介（非 AA）**与
  胶水地址，而不是父区“知道”的最终地址；委派点下残留的普通记录会阻塞发布。
- **名字不存在 ≠ 名字存在但无此类型**：预览明确区分 `NXDOMAIN` 与 `NODATA`
  （NOERROR + 空 Answer + Authority 里的 SOA），并正确处理空非终端（ENT）。
- **通配不是任意层级的字符串匹配**：`*.zone` 只合成“比已存在节点恰好多一层”的名字；
  跨多层缺失、或已存在中间节点的兄弟名都不会被错误匹配，预览会标出命中的通配拥有者。
- **别名链要能看清终点**：CNAME 链逐跳展示来源（精确/通配）、是否仍在区内，以及在何处因
  区外目标、环、目标无此类型或目标不存在而停止。
- **草稿多改、多人/多窗口不乱**：草稿有单调 `revision` 乐观锁，较早打开的窗口不能静默
  覆盖后来的保存；发布是服务端一次性原子落盘，刷新不会看到“半新 SOA、半旧记录”；历史
  版本不可变，回看旧版本查询用的是当时冻结的数据，不会被当前记录倒灌。

## 快速开始

```bash
npm install
npm run dev          # 同时起 API(5174) 与 Vite(5173)，打开 http://localhost:5173
```

生产模式（单端口托管前端 + API）：

```bash
npm run build        # tsc 编译服务端 + vite 构建前端
npm start            # http://localhost:5174
```

所有数据保存在本机 `data/state.json`（写临时文件后 `rename` 原子替换）。删除该文件即恢复
内置示例区域 `lab.internal.`。启动不依赖任何外部 DNS 或网络服务。

## 三个主操作面

1. **记录与草稿**：查看区域起点（SOA/NS）与各拥有者名下的记录集（委派点、起点有标记）；
   新增/编辑/删除都只写入草稿；实时校验列出阻塞错误与警告，错误可归因到草稿改动编号；
   通过校验后才能发布，也可一键回到已发布版本。
2. **查询预览**：输入查询名与类型，左右对照**已发布版本**（可选任意历史版本）与**当前
   草稿**。每个结果给出应答类别徽标、AA/RCODE、Answer/Authority/Additional 三段记录及
   每条记录的**出处**（精确名字 / 通配合成 / 胶水 / 否定应答 SOA）、CNAME 链、最近包围
   节点与命中通配。下方“查询样例”表随区域持久化，逐条标注本次草稿相对已发布**哪些样例
   会变、为什么变**。
3. **版本对照**：列出不可变的已发布版本（发布时间、SOA serial、备注），选择任意旧版本
   与当前草稿做按名字的差异对照，并可直接跳到该名字的历史查询。

## 应答类别（预览中可直接辨认）

| 类别 | 含义 | AA |
|---|---|---|
| `ANSWER` | 本区给出最终数据（含在本区内终结的 CNAME 链） | 是 |
| `NODATA` | 名字在区内存在（精确或 ENT），但没有所问类型；SOA 否定应答 | 是 |
| `NXDOMAIN` | 名字在区内不存在；SOA 否定应答 | 是 |
| `CNAME_MISS` / `CNAME_NXDOMAIN` | 别名链终点无此类型 / 终点名字不存在 | 是 |
| `CNAME_LOOP` | 别名自引用或成环，链在本区停止 | 是 |
| `CNAME_EXTERNAL` | 别名指向区域外，本区只负责到 CNAME 为止 | 否 |
| `REFERRAL` | 命中子域委派，父区给 NS（Authority）与胶水（Additional） | 否 |
| `OUT_OF_ZONE` | 查询名不属于本区域，拒绝作答（REFUSED） | 否 |

## 并发与一致性是怎么做的

- **草稿乐观锁**：每次保存必须带 `baseRevision`；服务端串行化所有写操作（单进程互斥链），
  revision 不符即返回 `409 REVISION_CONFLICT` 与当前 revision，旧窗口保存失败，不会覆盖。
- **发布原子化**：发布把 SOA serial 递增、整份记录冻结为新 `PublishedVersion`，草稿对齐并
  再推进一个 revision；状态整文件原子替换，任何时刻读到的都是一个完整版本。
- **历史不可变**：查询接口的 `source` 取 `draft`、`published`（最新）或**具体版本 id**；
  历史版本数据随发布时快照保存，不随后续编辑改变。
- **多窗口感知**：前端 4 秒轮询 `/api/boot`，发现草稿在本窗口之外更新会提示载入最新版。

## 技术栈与布局

TypeScript + React 18 + Vite（前端）/ Node.js + Express（后端），共享类型在 `shared/`。

```
shared/types.ts          前后端契约：记录、草稿操作、应答、版本
server/dns/name.ts       域名规范化、区域归属、通配“一层”规则
server/dns/rdata.ts      各 RR 类型 rdata 解析/渲染
server/dns/resolver.ts   权威查询：ENT/通配/委派+胶水/CNAME 链/否定应答
server/dns/validate.ts   发布前语义校验（冲突、委派、起点），错误归因到草稿操作
server/store.ts          原子持久化、revision 锁、发布快照
server/query-service.ts  按版本解析与样例影响比对
server/main.ts           HTTP API + 生产静态托管
client/                  React 三个标签页与应答可视化
```

## 内置验收脚本

```bash
npx tsx server/semantic-check.ts   # 权威语义：30 项（通配层级、NODATA/NXDOMAIN、委派、CNAME 终点、校验归因）
npx tsx server/e2e-check.ts        # HTTP 全流程：29 项（保存/对照/并发冲突/发布阻塞/版本冻结/委派变更/持久化）
```

> e2e 脚本假设从干净状态开始；如重复运行，先删除 `data/state.json`。

## 建议的手工验收路径

1. 首次发布基线 → 用同一批查询样例对照草稿与已发布。
2. 把 `www` 的 CNAME 从 `app` 改到 `mail`，看同一条 `www/A` 在两列里的链路与地址差异、
   样例表把变化标出来。
3. 给新子域（如 `asia`）加 NS 和胶水：先故意再给 `host.asia` 加一条 A，看到发布被
   `BELOW_CUT_DATA` 阻止并归因到那条改动；删掉后查询 `x.asia/A` 变为转介（非 AA、带胶水）。
4. 查 `random/A`（命中 `*`）与 `a.b/A`（跨多层不命中）体会通配边界；查 `app/AAAA`
   （NODATA）与 `zz.nope/A`（NXDOMAIN）体会两类否定。
5. 开两个浏览窗口：后窗口保存后，前窗口再保存会收到冲突提示；发布后在“版本对照”里选旧
   版本重放查询，确认旧结果不被当前记录倒灌。
